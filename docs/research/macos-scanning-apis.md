# Research: macOS scanning API landscape (ImageCaptureCore, SANE, alternatives)

_Generated by research agents, July 28 2026. Confidence: high_

## Findings

ALL API FACTS BELOW VERIFIED AGAINST PRIMARY SOURCES ON A REFERENCE MACHINE (macOS 26 "Tahoe", Xcode MacOSX26.sdk headers at /Applications/Xcode.app/.../MacOSX26.sdk/System/Library/Frameworks/ImageCaptureCore.framework/Versions/A/Headers/, and the installed fi driver at /Library/Image Capture/Devices/FujitsuScanner.app + /opt/pfufs).

== 1. ImageCaptureCore scan parameter surface (exact symbols) ==
Discovery/session: ICDeviceBrowser (browsedDeviceTypeMask: ICDeviceTypeMaskScanner | location masks incl. ICDeviceLocationTypeBonjour=0x400 for network devices), delegate deviceBrowser:didAddDevice:moreComing:. ICScannerDevice.requestOpenSession — EXCLUSIVE access; other-client release signaled via scannerDeviceDidBecomeAvailable:; busy errors ICReturnScannerInUseByLocalUser=-9925 / ...RemoteUser=-9926. In Swift 6.2, select the feeder with `scanner.requestSelect(.documentFeeder)` and receive `scannerDevice(_:didSelect:error:)`.
Live M0 caveat: the fi-8170 driver issued an initial functional-unit-selection callback whose functional-unit object was null even though ImageCaptureCore imports that parameter into Swift as nonnull. Do not dereference it blindly. Wait for `deviceDidBecomeReady(_:)`, confirm that `.documentFeeder` is available, and keep a nullable Objective-C boundary (or otherwise guard the runtime value) before configuring the later valid feeder callback.
Duplex/ADF (ICScannerFunctionalUnitDocumentFeeder): supportsDuplexScanning (RO), duplexScanningEnabled (RW), documentLoaded (RO — documented as live ADF paper-present detection), oddPageOrientation/evenPageOrientation (ICEXIFOrientationType), reverseFeederPageOrder (RO). Treat `documentLoaded` as advisory only: in the live M0 run it reported `true`, but the subsequent `requestScan()` completed with the driver's "No documents in the ADF paper chute" error. The scan completion/error is authoritative.
Resolution: supportedResolutions/preferredResolutions (NSIndexSet, DPI), resolution (RW NSUInteger), nativeXResolution/nativeYResolution; scaleFactor + supportedScaleFactors.
Bit depth/pixel: ICScannerBitDepth {1,8,16}, supportedBitDepths, bitDepth; ICScannerPixelDataType {BW=0,Gray=1,RGB=2,Palette,CMY,CMYK,YUV,YUVK,CIEXYZ}; B&W threshold: acceptsThresholdForBlackAndWhiteScanning / thresholdForBlackAndWhiteScanning (0–255).
Document size/area: ICScannerDocumentType (~78 values: A4=1, USLetter=3, A6=13, BusinessCard=53, photo 3R..S12R, film sizes), supportedDocumentTypes (NSIndexSet), documentType (RW), documentSize (RO ICSize); free-form scanArea (RW ICRect) + measurementUnit (ICScannerMeasurementUnit inches/cm/picas/points/twips/pixels); scanAreaOrientation is documented as NOT used by the DocumentFeeder subclass; physicalSize (RO).
OVERSCAN: there is NO overscan property anywhere in ImageCaptureCore public headers (grepped all headers, macOS 26 SDK — zero hits). On the fi driver, "Overscan" is a menu value of the vendor "Cropping" feature (see §3); libsanepfufs.dylib exports PFU_CROPPING_LIST / PFU_CROPPING_LIST_NO_OVERSCAN option tables.
Transfer/delivery: ICScannerDevice.transferMode = ICScannerTransferModeFileBased(0) | MemoryBased(1); file mode: downloadsDirectory (NSURL), documentName, documentUTI (header: "kUTTypeJPEG, kUTTypeJPEG2000, kUTTypeTIFF, kUTTypePNG etc." — the DRIVER encodes JPEG, no re-encode needed); memory mode: maxMemoryBandSize (UInt32) + scannerDevice:didScanToBandData:(ICScannerBandData: fullImageWidth/Height, bitsPerPixel, bitsPerComponent, numComponents, bigEndian, pixelDataType, colorSyncProfilePath, bytesPerRow, dataStartRow, dataNumRows, dataSize, dataBuffer).
Per-page callback: Objective-C `scannerDevice:didScanToURL:` imports into Swift 6.2 as `scannerDevice(_:didScanTo:)` — the header states explicitly "If selectedFunctionalUnit is a document feeder, then this message will be sent once for each scanned page" — perfect hook for counter-based renaming (scan_NNNNNN_F/B). Old didScanToURL:data: deprecated since 10.7. Completion: scannerDevice:didCompleteScanWithError:. requestScan runs the feeder until empty; cancelScan aborts. Progress: scanProgressPercentDone, ICScannerFunctionalUnitState bitmask, ICScannerStatusWarmingUp/WarmUpDone strings. Overview scans unsupported on feeders (canPerformOverviewScan=NO). Hardware buttons: ICButtonTypeScan/Mail/Copy/... constants; fi driver has a "Scan button monitor" vendor toggle.
Errors (ImageCaptureConstants.h, ICErrorDomain): ICReturnReceivedUnsolicitedScannerErrorInfo=-9933 (how mid-scan driver errors — multifeed/jam — surface; seen in the wild: NAPS2 issue #171), ICReturnScannerFailedToCompleteScan=-9931, ICReturnScanOperationCanceled=-9924, ICReturnConnectionDriverExited=-21350 family. The fi driver maps SANE statuses to localized strings shipped in FujitsuScanner.app/Contents/Resources/en.lproj/Localizable.strings: "Multifeed detected.", "Paper jammed in the ADF.", "No documents in the ADF paper chute.", "Scanner cover is open." — these arrive in the NSError.

== 2. Alive & supported? YES ==
Framework fully present in the macOS 26 SDK; every scanner symbol annotated IC_AVAILABLE(macos(10.4)) with NO deprecation (only ICRunLoopMode and didScanToURL:data: are deprecated). Scanner classes are IC_UNAVAILABLE(ios) — Mac-only. ObjC delegate API, clean Swift import (wrap in actor + AsyncStream; no async/await natively). ImageKit's IKScannerDeviceView (canned scan UI, 10.6+) also still ships in macOS 26 — usable via NSViewRepresentable but unnecessary. PROOF OF LIFE ON THIS EXACT STACK: the installed PFU ICA module (com.fujitsu.fiscanner.ica v2.4.1, built April 2025, "Copyright PFU Limited 2019-2025", universal arm64+x86_64, links ICADevices.framework + ImageIO) produced real scans via Image Capture on the reference machine: 2480x3496 @600dpi RGB JPEG = exactly A6@600dpi (A6=13 is in the driver's ICAP_SUPPORTEDSIZES along with A4,B5,USLetter,USLegal,A5,USExecutive,JIS-B6,BusinessCard).
TWAIN: TWAIN.framework physically still exists in macOS 26 SDK and /System/Library/Frameworks (verified) — no formal "removed in macOS 14" API event found; what actually died is the vendor TWAIN/legacy-ICA driver ecosystem (Canon etc. stopped at 10.13-era drivers; Adobe dropped TWAIN on Mac). Do not build on TWAIN. The legacy ICADevices.framework module architecture (ICD_ScannerCalls.h) also still ships in the macOS 26 SDK — PFU's April-2025 module is the living example that Apple still supports third-party ICA scanner modules.
eSCL/AirScan: macOS's driverless scanning IS fronted by the same ImageCaptureCore API — eSCL scanners appear via ICDeviceBrowser as Bonjour-located ICScannerDevices (ICDeviceLocationTypeBonjour). NAPS2 states "Apple's ImageCaptureCore provides access to TWAIN and ESCL scanners on Mac". One client codebase gets vendor-ICA + driverless-eSCL hardware. Caveat: the fi-8170 datasheet lists NO eSCL/AirScan; its official Mac path is "Image Scanner Driver for macOS (ICA)". PFU's own driver supports the fi-8170 over LAN too (devicetable.xml <isnet>1</isnet>).
Sandbox/App Store: ImageCaptureCore is MAS-legal. Friction data point: Apple forum thread (macOS 15.1.1, unanswered) reports a hardened-runtime app with com.apple.security.device.usb + NSCameraUsageDescription seeing iOS devices but not USB scanners via ICDeviceBrowser. Recommend Developer ID + hardened runtime (no sandbox) for v1; treat sandbox/MAS as a later spike with early discovery testing. (macOS 14+ sandboxed USB uses com.apple.security.device.usb.)

== 3. Vendor-specific driver options: PUBLICLY VISIBLE to any ImageCaptureCore client ==
Mechanism (verified end-to-end locally): ICScannerFunctionalUnit.vendorFeatures → NSArray<ICScannerFeature*>; concrete classes ICScannerFeatureEnumeration (currentValue settable, values, menuItemLabels, menuItemLabelsTooltips), ICScannerFeatureRange (currentValue, min/max/stepSize), ICScannerFeatureBoolean (value), each with internalName/humanReadableName/tooltip. The ICA module publishes these via a literal "vendor features" array in its scanner-properties dictionary (present in FujitsuScanner.app's ScannerProperties.plist template) and implements FujitsuScanner::getValueForVendorFeature / setValuesForVendorFeaturesFromDictionary (symbols in the module binary). Image Capture's details pane simply renders this same array — nothing is private to the driver UI.
The fi driver's complete vendor feature set (binary strings + en.lproj/Localizable.strings) is represented in static resources by aliases such as FEATURE_CROPPING, FEATURE_MULTIFEED_DETECTION, FEATURE_BLANK_PAGE_SKIP, FEATURE_DROPOUT_COLOR, FEATURE_PREPICK, FEATURE_SCANBUTTON_MONITOR, FEATURE_SHARPNESS, and FEATURE_TONE_ADJUSTMENT. The live fi-8170 runtime exposed lowercase `internalName` values instead: `cropping`, `multifeed_detection`, `blank_page_skip`, `dropout_color`, `prepick`, `scan_button_monitor`, `sharpness`, and `tone_adjustment`. Match case-insensitively and canonicalize an optional `FEATURE_` prefix rather than depending on either spelling.
Menu meanings remain: Cropping → "None (with black background)" / "None (with white background)" / "Auto (Speed emphasis)" / "Auto (Accuracy emphasis)" / "Overscan"; Multifeed detection → Off / On (Overlapping) / On (Length) / On (Overlapping+Length) — its tooltip explicitly warns that thick/plastic cards can false-trigger overlap detection (directly relevant to sleeved cards: default Off); Blank page skip → Off + 5 sensitivity levels; Dropout color → White/Red/Green/Blue/None; Prepick → Off/On; Scan button monitor → Off/On; Sharpness → None/Smoothing/Emphasis 1-3/Descreen 1-4; Tone adjustment → None/Normal/Soft/Sharp/Bright. In the live menu, raw `prepick = 0` is **Off**. Prefer matching the localized menu label for discovery, then persist the validated runtime value for that installed driver version.
All enumerations are programmatically settable before `requestScan()`. The live runtime also returned duplicate vendor-feature objects with identical names, values, and menus. Coalesce identical snapshots for display, but apply and verify the requested value across every matching runtime object; treat conflicting duplicates as a configuration failure.
fi-8170 device identity in driver: USB VID 0x04c5 PID 0x15ff (Fujitsu) and VID 0x05ca PID 0x03d8 (Ricoh-branded), in DeviceMatchingInfo.plist.

== 4. Alternatives ==
(a) SANE open-source: sane-backends' `fujitsu` backend lists fi-8170 as status "good" (USB 0x04c5/0x15ff) — a real hedge. Cons on macOS: libusb device claiming can contend with Apple's ICA daemon, ship-your-own libsane + udev-less quirks, GPL linkage considerations, no vendor image processing (PFU Clear Image Capture stays in firmware/driver), no sandbox story.
(b) Driving PFU's libsanepfufs.dylib directly: /opt/pfufs/lib/libsanepfufs.dylib is a PROPRIETARY SANE BACKEND (universal arm64+x86_64; exports standard sane_pfufs_init/open/start/read/cancel + get_option_descriptor; links only libxml2/CF/IOKit/libc++; internally dlopens a second-stage g_sane_pfufs2_* and libjpeg-turbo 2.1.1; contains per-model option tables PFU_DEVICE_OPTION_* incl. fi-8xxx, PFU_CROPPING/BACKGROUND/BW_MODE/BLANK_PAGE_SKIP/JPEG_QUALITY lists, and DeskewAndCropping hooks). dlopen-able in principle — but undocumented, license-restricted, version-coupled. Classify as research spike only, never the shipping path.
(c) ExactScan: ships its own userspace drivers for 500+ models inside the app (no vendor driver needed) and can even act as a TWAIN source for other apps — proves the own-driver route exists but is a multi-year moat; not for v1.
(d) NAPS2 (most active OSS cross-platform scanner app): on macOS its DEFAULT driver is Driver.Apple = ImageCaptureCore; also offers Driver.Sane (NAPS2.Sane.Binaries) and Driver.Escl on Mac. Independent validation that ImageCaptureCore-first + SANE-fallback is the correct Mac architecture. (e) VueScan: own reverse-engineered drivers incl. fi-8170; dated UI — the competitor to beat, not a stack to reuse.

== 5. SwiftUI viability ==
Regular (non-document-based) SwiftUI app: batch/session model with its own store (SwiftData or JSON sidecar) + files on disk; NSDocument fights the append-only batch + release-to-Drive workflow. Wrap the ICScannerDevice delegate in an actor/@MainActor-observable publishing per-page events through AsyncStream. Thumbnails: a 600dpi A6 frame decodes to ~26MP (~35MB BGRA) — never bind originals to the grid; downsample-on-decode via CGImageSourceCreateThumbnailAtIndex (kCGImageSourceThumbnailMaxPixelSize≈512, kCGImageSourceCreateThumbnailFromImageAlways) or QuickLookThumbnailing off-main, cache in NSCache; LazyVGrid comfortably handles hundreds of pre-decoded small CGImages (NSCollectionView via NSViewRepresentable is the escape hatch at multi-thousand scale). Background pipeline: bounded TaskGroup (≈ half activeProcessorCount for 26MP frames) doing crop/rotate; Vision VNDetectRectanglesRequest finds the bright card in the driver's black-background frame (same luminance-threshold logic as the proven reference implementation — ports 1:1); geometry via vImage or CoreImage(Metal CIContext); write via CGImageDestination with kCGImagePropertyDPIWidth/Height=600 and lossy quality ~0.95.

Key spec-relevant gotchas: exclusive device session (Image Capture app left open blocks the device); requestScan drains the feeder — a "batch" is repeated requestScan cycles, with `documentLoaded` useful only as an advisory prompt and the request/completion result authoritative; rename per page inside Swift's `scannerDevice(_:didScanTo:)` callback (driver's own naming is documentName-based, "Scan N.jpeg" pattern); multifeed/jam arrive as NSError (-9933/-9931) with driver-localized text; scanAreaOrientation ignored by feeder units — use odd/evenPageOrientation; fi-8170 = 600dpi optical, 50–600dpi in 1-dpi steps (1200 interpolated), USB 3.2 Gen1 + GbE, 100-sheet ADF, 70ppm/140ipm @200/300dpi.

## Recommendation

PRIMARY STACK: ImageCaptureCore against the installed PFU fi Series ICA driver. Concretely: ICDeviceBrowser (scanner mask) → ICScannerDevice.requestOpenSession → wait for device ready → requestSelectFunctionalUnit(.documentFeeder) → safely ignore a null selection callback and configure the later valid feeder {duplexScanningEnabled=true, resolution=600, pixelDataType=.RGB, bitDepth=.depth8Bits, documentType=.typeA6 (or scanArea rect), transferMode=.fileBased, documentUTI=UTType.jpeg, downloadsDirectory=staging} plus vendorFeatures set programmatically (Cropping="None (with black background)", Multifeed detection=Off for sleeved cards, Blank page skip=Off, Prepick=Off, whose live raw value is 0) → requestScan per batch; each Swift `scannerDevice(_:didScanTo:)` callback does counter naming (scan_NNNNNN_F/B.jpg) and feeds the review grid; didCompleteScanWithError + -9933 handling drives the misfeed UX. This is Apple's supported, non-deprecated path on macOS 26, reproduces the already-proven Image Capture workflow on the reference machine, delivers driver-encoded 600dpi JPEG per page with no re-encode, and exposes every PaperStream-relevant driver toggle through the public vendorFeatures API. The same client code fronts driverless eSCL/AirScan network scanners later for free (second-hardware roadmap).
FALLBACK STACK: open-source SANE `fujitsu` backend (fi-8170 rated "good") vendored as an XPC helper — the hedge if PFU abandons the ICA driver or Apple breaks the ICA module architecture; NAPS2 proves ImageCaptureCore-primary + SANE-fallback is viable. Explicitly reject: TWAIN (dead ecosystem, framework vestigial), building own drivers (ExactScan-scale moat), and shipping against PFU's proprietary libsanepfufs.dylib (dlopen works technically — record as a research-spike appendix only, license-blocked for distribution).
SPEC DECISIONS TO ADOPT: regular (non-document) SwiftUI app with batch store; actor-wrapped scanner service emitting AsyncStream page events; file-based transfer (not memory bands) since the driver's JPEG is the desired artifact; downsample-on-decode thumbnail pipeline (CGImageSource, ~512px, NSCache) into LazyVGrid; Vision rectangle detection for auto-crop of the black-background A6 frame; distribution via Developer ID + hardened runtime for v1 (defer App Sandbox/MAS pending an early discovery-under-sandbox spike — one open Apple-forum report of sandboxed scanner discovery failure on macOS 15.1). Also spec the exclusive-session UX (detect/queue on ICReturnScannerInUseByLocalUser, auto-resume via scannerDeviceDidBecomeAvailable) and a repeated-scan batch loop that uses `documentLoaded` as a hint, never as proof that a scan can proceed.
